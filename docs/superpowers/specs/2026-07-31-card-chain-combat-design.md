# 牌链自动战斗系统设计决策记录

**日期：** 2026-07-31
**状态：** 设计草案已收敛——待用户审阅后进入实现计划
**范围：** 单怪物事件、探索阶段牌链编排、自动战斗结算

## 1. 设计目标

MonoCard 的战斗不是传统的战斗中出牌系统。玩家在探索阶段获取、放置、连接和调整卡牌；遇到怪物事件后，系统自动执行当前牌链，并将结果反馈给玩家。

核心体验是：

> 玩家通过探索中的牌链编排，主动塑造并理解自动战斗的结果。

战斗事件的职责是验证当前方案，而非要求玩家在结算过程中进行额外操作。

## 2. 核心循环

```text
探索、获取和调整卡牌
  -> 在棋盘上按连接规则编排牌链
  -> 选择进入单个怪物事件
  -> 自动执行一次遭遇结算
  -> 应用胜利、撤退或战败结果
  -> 返回探索或进入失败流程
```

棋盘上的卡牌必须接在上一张卡牌的顶部。后续将通过带方向的桥梁 UI 明确表达连接关系、执行顺序、牌链首尾和可能的断链状态。

## 3. 战斗服务边界

新增独立的 `CombatService` 作为唯一的战斗规则入口。

它接收：

- 玩家当前运行时战斗状态；
- 按牌链执行顺序排列的卡牌实例；
- 怪物当前运行时状态与行动定义。

它在内部计算一次怪物遭遇，并返回 `CombatResult`。服务不得直接依赖棋盘节点、卡牌 UI 或事件界面，也不得直接删除棋盘中的卡牌。

调用方（怪物事件或游戏管理器）负责：

- 准备牌链顺序和当前状态；
- 播放动画与展示日志；
- 应用正式结算后的属性变化；
- 根据结果执行惩罚、奖励、事件完成或失败流程。

服务应支持同一结算逻辑的两种用途：

- **正式结算：** 计算并由外层应用结果；
- **后续预览：** 以相同规则模拟但不应用状态。首个 Demo 不要求提供完整精确预览。

## 4. 逻辑回合、行动批次与自动执行

玩家不在战斗中进行点击、选牌或确认。玩家回合和怪物回合只是内部的逻辑结算顺序。

普通情况下：

```text
玩家结算一张卡牌
  -> 若怪物死亡，立即胜利并停止
  -> 当前玩家行动批次结束
  -> 怪物行动一次
  -> 若玩家 HP 归零，立即战败并停止
  -> 继续下一张卡牌
```

牌根可以把相邻的多张卡牌放入同一个玩家行动批次：

```text
玩家卡牌 A
玩家卡牌 B
  -> 怪物行动一次
```

因此，怪物不是在每张卡牌之后无条件行动，而是在当前玩家行动批次结束后行动。若玩家卡牌直接击杀怪物，则立即结束战斗，不再结算批次中的剩余卡牌，也不触发怪物反击。

牌链全部结算后，若双方仍存活，则本次遭遇以撤退结束。

## 5. 卡牌基础效果与可组合效果规则

首版卡牌基础字段的语义：

- `damage`：对怪物造成伤害；
- `defense`：为玩家增加本次遭遇内的护甲；
- `heal`：恢复玩家 HP。

每张卡牌都由以下部分组成：

```text
基础效果
  + 0 到多个卡牌效果规则
```

这里不区分“普通卡牌”和“特殊卡牌”。特殊的是卡牌携带的效果规则，而不是卡牌类型本身。

卡牌效果规则用于表达：

- 联动效果；
- 条件效果；
- 基于牌链位置的效果；
- 基于玩家或怪物当前状态的效果；
- 基于已经结算卡牌历史的效果。

示例：

```text
上一张带有 WEAPON 标签
  -> 当前卡牌伤害乘以 2

玩家 HP 低于 50%
  -> 当前卡牌额外恢复 3 点 HP

当前是牌链最后一张
  -> 当前卡牌额外获得 2 点护甲
```

卡牌配置不再使用单一的 `effect_algorithm` 表达全部逻辑，而是使用可组合的 `effect_rules` 列表。现有 `damage`、`defense`、`heal` 字段首版继续保留，由基础效果构建器读取；后续再根据卡牌数量决定是否迁移为通用效果资源数组。

## 6. 卡牌效果规则的结构

卡牌效果规则采用组合模式、策略模式和 Specification 思路组合设计：

```text
CardRule
  ├─ CardCondition
  └─ CardOperation
```

`CardCondition` 只负责读取 `CardResolutionContext` 并判断条件是否成立；`CardOperation` 只负责修改当前卡牌的临时效果草稿或追加额外 `CombatEffect`。规则不直接修改玩家、怪物、棋盘或 UI 状态。

首版建议支持的条件：

- `PreviousCardHasTag`；
- `PreviousCardHasType`；
- `HasResolvedCardWithTag`；
- `ResolvedCardCount`；
- `PlayerHpRatio`；
- `MonsterHpRatio`；
- `IsFirstCard`；
- `IsLastCard`。

首版建议支持的操作：

- `AddDamage`；
- `MultiplyDamage`；
- `AddDefense`；
- `AddHeal`；
- `AddCombatEffect`。

每张卡牌的规则按 `effect_rules` 数组顺序执行。所有条件读取当前卡牌开始结算时的战斗上下文快照；规则只能影响当前卡牌，不直接修改未来卡牌。

当前卡牌的结算过程为：

```text
读取基础 damage / defense / heal
  -> 创建 CardResolutionDraft
  -> 按顺序执行满足条件的 CardRule
  -> 将草稿转换为 CombatEffect
  -> 由 CombatService 依次执行效果
```

复杂到不适合由通用条件和操作组合的效果，可以实现一个自定义 `CardRule`，但仍必须遵守同样的上下文读取和效果输出边界。

## 7. 牌根的定位

牌根同时具备两种能力：

```text
普通卡牌效果
  + 牌链规则
```

因此牌根也可以拥有基础 `damage`、`defense`、`heal` 和 `effect_rules`。除此之外，牌根可以提供 `root_chain_rules`，用于修改整条牌链的行动批次或怪物行动时机。

牌根不应只是普通数值卡，而应作为“牌链规则修改器”。它的长期作用是使不同构筑形成不同的牌链风格，而不是把所有玩家导向同一套攻击卡模板。

首版牌根约束：

- 牌链只有一张牌根；
- 牌根位于牌链起点；
- 牌根在战斗开始时结算自身效果并注册牌链规则；
- 牌根不单独触发怪物行动；
- 牌根规则只在本次遭遇中有效；
- 首版不支持多个牌根规则的复杂叠加。

**已确认：** 牌根触发的相邻两张武器牌连续结算；两张牌之间不触发怪物行动，怪物只在这组连击完成后行动一次。非相邻的两张武器牌不能组成该连击；如果第一张匹配卡之后出现非匹配卡，连击批次结束。

## 8. 怪物行动

怪物必须提供统一的 `next_action()` 接口。战斗服务只消费下一项行动，不应绑定怪物采用固定顺序、随机选择还是条件选择。

职责分离：

```text
怪物：选择下一步行动（next_action）
战斗服务：解释该行动对双方状态造成的结果
```

**已确认（Demo）：** 所有怪物按配置行动列表固定循环；每次遭遇从第一项行动开始。后续可替换为：

- 随机行动；
- 按怪物 HP 选择；
- 按玩家状态选择；
- 阶段性行动；
- 根据上一张玩家卡调整行动。

基础行动的数值直接取 `MobAction.value`。当前约定：

- `ATTACK`：对玩家造成 `value` 点伤害；
- `DEFEND`：怪物获得 `value` 点护甲；
- `HEAL`：怪物恢复 `value` 点 HP；
- `BUFF`、`DEBUFF`、`SPECIAL`：保留接口，暂不要求在 Demo 怪物数据中投入实际玩法。

## 9. 战斗结果

`CombatResult` 至少应表达：

- `outcome`：`VICTORY`、`RETREAT` 或 `DEFEAT`；
- 玩家和怪物的结算后状态；
- 按时间顺序排列的结算步骤/战斗日志；
- 实际结算的卡牌数量；
- 可扩展的惩罚列表 `penalties`。

结果定义：

| 结果 | 条件 | 后果 |
|---|---|---|
| `VICTORY` | 怪物 HP 归零 | 停止结算；事件进入已完成状态，外层按怪物配置发放金币和卡牌奖励。 |
| `RETREAT` | 牌链耗尽，玩家和怪物均存活 | 结束遭遇；生成撤退惩罚。 |
| `DEFEAT` | 玩家 HP 归零 | 立即停止；Demo 中结束本局探索，并由外层进入失败结算与重新开局流程。 |

## 10. 胜利奖励与事件完成

怪物被击杀后，本次怪物事件进入已完成状态，不再允许再次挑战。事件层负责采用现有怪物配置处理奖励：

```text
MobData.gold_reward
MobData.card_rewards
```

战斗服务只产生胜利结果和结算日志；金币、卡牌的实际发放以及已完成事件的地图表现由外层处理。

**已确认：** 获得的卡牌奖励进入玩家手牌／待放置区。玩家在后续探索中自行决定是否以及如何把它们纳入牌链；奖励不会自动追加到牌链末尾。
## 11. 惩罚系统

战斗结果不应使用“是否删除末尾卡”这样的专用字段，而应返回通用的 `CombatPenalty` 列表。

当前 Demo 的唯一惩罚：

```text
RETREAT
  -> REMOVE_CARD(amount = 1, target = TAIL_OF_CARD_CHAIN)
```

这表示：牌链耗尽但未击败怪物时，事件层从牌链末尾移除一张卡牌。

未来可以扩展的惩罚包括：

- `EXHAUST_CARD`：暂时使卡牌不可用；
- `CURSE_CARD`：为卡牌添加负面效果；
- `DAMAGE_BRIDGE`：损坏牌链中的桥梁/连接；
- `LOCK_CARD`：暂时禁止卡牌移动或触发；
- `LOSE_RESOURCE`：失去金币或探索资源；
- `MONSTER_ESCALATE`：强化怪物或改变其状态。

删除末尾卡牌适合快速验证设计，但长期必须观察它是否被玩家利用为无成本删废牌手段。

## 12. 状态持续时间

普通护甲是战斗内临时状态，不等同于 HP。

当前推荐边界：

```text
玩家 HP：跨遭遇保留
怪物 HP：跨撤退保留
玩家护甲：遭遇结束后清除
怪物护甲：遭遇结束后清除
普通 BUFF / DEBUFF：遭遇结束后清除
```

如果未来需要跨遭遇的防御或状态，必须显式定义为永久、装备或区域状态，不能和普通战斗护甲混用。

玩家不直接攻击怪物；首版应避免让 `player.attack` 处于半生效状态。它可以暂时不参与结算，或在后续改造成语义明确的卡牌伤害倍率属性。

## 13. 信息公开与反馈

自动战斗必须可解释，但不应在首版变成完全精确的结果计算器。

进入怪物事件前建议公开：

- 怪物名称与当前 HP；
- 当前玩家 HP；
- 当前牌链的执行顺序；
- 怪物下一次行动；
- 风险提示；
- 撤退可能触发的惩罚。

战斗结束后应提供完整动画和可回顾的战斗日志，说明：

- 每张卡如何生效；
- 每次怪物行动造成了什么变化；
- 最终剩余 HP；
- 成功或失败的具体原因；
- 实际施加的惩罚。

为避免打断探索节奏，应提供快速结算或跳过动画的方式，同时保留查看日志的能力。

## 14. Demo 边界

首个可玩 Demo 聚焦验证“牌链编排是否有趣”：

- 单个怪物目标；
- 自动结算；
- 卡牌伤害、防御、治疗；
- 怪物攻击、防御、治疗；
- 行动步骤日志；
- 胜利、撤退、战败三种结果；
- 当前唯一惩罚：删除牌链末尾一张卡；
- 棋盘牌链方向、首尾与桥梁 UI；
- 快速结算或跳过动画。

Demo 暂不要求：

- 多怪物；
- 完整精确战斗预览；
- 复杂随机行动；
- 多个牌根规则的复杂叠加；
- 复杂玩家攻击属性；
- 多个同时生效的惩罚；
- 多阶段 Boss；
- 复杂奖励经济。

## 15. 试玩验证项

以下内容不是首版接口的阻塞决策，而是需要通过试玩观察的平衡问题：

- 撤退后暂不立即强化怪物；
- 先以怪物 HP 保留和删除牌链末尾卡牌验证核心循环；
- 试玩后再决定是否需要加入怪物强化，以抑制玩家机械磨血；
- 观察删除末尾卡牌是否会被玩家主动利用为无成本删废牌手段。

进入实现计划前，核心规则和数据边界已经确定；上述项目属于 Demo 运行后的平衡迭代。

## 16. 设计原则

1. 战斗自动执行，但结果必须可解释。
2. 牌链越长可以越危险，但应通过牌根和连锁获得相应收益。
3. 所有卡牌都由基础效果和可组合的效果规则构成，不把卡牌划分为“特殊卡牌”才能拥有联动。
4. 条件读取当前卡牌开始结算时的上下文，效果规则只影响当前卡牌的临时效果草稿。
5. `CombatEffect` 是统一的效果命令，由 `CombatService` 负责执行、记录和判断死亡。
6. 牌根应改变牌链规则，而非仅提供更高数值；牌根自身效果和牌链规则分开处理。
7. 惩罚描述“发生什么后果”，由外层应用，不直接耦合棋盘操作。
8. 战斗服务使用运行时副本计算，不直接修改棋盘、卡牌 UI、玩家正式状态或怪物事件。
9. 先验证牌链编排的核心乐趣，再增加行动、状态和奖励复杂度。
